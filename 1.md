### 2.3 Table 1 — `tenants`
 
Represents every SaaS founder who has signed up to ChurnGuard.
 
```sql
CREATE TABLE tenants (
    id                   UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
    owner_id             UUID        NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
    company_name         VARCHAR(255) NOT NULL DEFAULT 'My SaaS Product',
    company_url          VARCHAR(500),

    stripe_api_key       TEXT,

    trial_ends_at        TIMESTAMPTZ  NOT NULL DEFAULT (NOW() + INTERVAL '14 days'),
```

### 2.5 Table 3 — `cancellation_sessions`
 
One row per cancellation attempt, regardless of outcome.
This is the core event log — every widget interaction creates a row.
 
```sql
CREATE TABLE cancellation_sessions (
    id                   UUID         PRIMARY KEY DEFAULT gen_random_uuid(),
    tenant_id            UUID         NOT NULL REFERENCES tenants(id) ON DELETE CASCADE,
    -- Short-lived HMAC-SHA256 token for session verification
    session_token        VARCHAR(512) NOT NULL UNIQUE,
    token_expires_at     TIMESTAMPTZ  NOT NULL,  -- 15 minutes from creation
    -- Stripe identifiers (provided by client's widget.js data attributes)
    customer_stripe_id   VARCHAR(255) NOT NULL,
    customer_email       VARCHAR(255) NOT NULL,
    subscription_id      VARCHAR(255),
    -- MRR tracking
    original_mrr_cents   INTEGER      NOT NULL DEFAULT 0,
    saved_mrr_cents      INTEGER      NOT NULL DEFAULT 0,
    -- Outcome
    status               session_status NOT NULL DEFAULT 'initiated',
    selected_reason      VARCHAR(255),
    custom_feedback      TEXT,
    applied_offer        VARCHAR(255),
    offer_type_applied   offer_type,
    -- Metadata
    origin_url           TEXT,   -- URL where widget.js fired (for origin validation)
    user_agent           TEXT,
    created_at           TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    completed_at         TIMESTAMPTZ
);
```

### 2.10 Row Level Security (RLS) Policies
 
```sql
-- Enable RLS on all 7 tables
ALTER TABLE tenants                   ENABLE ROW LEVEL SECURITY;
ALTER TABLE flow_configs              ENABLE ROW LEVEL SECURITY;
ALTER TABLE cancellation_sessions     ENABLE ROW LEVEL SECURITY;
ALTER TABLE webhook_events            ENABLE ROW LEVEL SECURITY;
ALTER TABLE churnguard_subscriptions  ENABLE ROW LEVEL SECURITY;
ALTER TABLE analytics_daily           ENABLE ROW LEVEL SECURITY;
ALTER TABLE notification_preferences  ENABLE ROW LEVEL SECURITY;
 
-- Stable helper: look up calling user's tenant ID
CREATE OR REPLACE FUNCTION get_my_tenant_id()
RETURNS UUID AS $$
    SELECT id FROM tenants WHERE owner_id = auth.uid() LIMIT 1;
$$ LANGUAGE sql SECURITY DEFINER STABLE;
 
-- ── tenants ──────────────────────────────────────────────────────────
-- Owners can do everything on their own row only
CREATE POLICY "tenants: owner full access"
    ON tenants FOR ALL
    USING (auth.uid() = owner_id);
 
-- ── flow_configs ──────────────────────────────────────────────────────
-- Owners can do everything on their own flow config
CREATE POLICY "flow_configs: owner full access"
    ON flow_configs FOR ALL
    USING (tenant_id = get_my_tenant_id());
 
-- The widget (anon role) needs SELECT to load survey config
-- We restrict to is_active = true to prevent loading inactive configs
CREATE POLICY "flow_configs: public select if active"
    ON flow_configs FOR SELECT
    USING (is_active = true);
 
-- ── cancellation_sessions ─────────────────────────────────────────────
-- Owners can read their own sessions
CREATE POLICY "sessions: owner read"
    ON cancellation_sessions FOR SELECT
    USING (tenant_id = get_my_tenant_id());
 
-- The widget (anon role) can INSERT a new session row
-- Security: session token verification is handled at the API layer, not RLS
CREATE POLICY "sessions: public insert"
    ON cancellation_sessions FOR INSERT
    WITH CHECK (true);
 
-- UPDATEs (applying offers, completing sessions) only via service_role key
-- in API routes — not accessible to anon or authenticated roles directly
 
-- ── webhook_events ────────────────────────────────────────────────────
CREATE POLICY "webhook_events: owner read"
    ON webhook_events FOR SELECT
    USING (tenant_id = get_my_tenant_id());
 
-- ── churnguard_subscriptions ──────────────────────────────────────────
CREATE POLICY "cg_subs: owner read"
    ON churnguard_subscriptions FOR SELECT
    USING (tenant_id = get_my_tenant_id());
 
-- ── analytics_daily ───────────────────────────────────────────────────
CREATE POLICY "analytics: owner read"
    ON analytics_daily FOR SELECT
    USING (tenant_id = get_my_tenant_id());
 
-- ── notification_preferences ─────────────────────────────────────────
CREATE POLICY "notif_prefs: owner full access"
    ON notification_preferences FOR ALL
    USING (tenant_id = get_my_tenant_id());
```

### 2.12 Database Triggers
 
```sql
-- ═══════════════════════════════════════════════════════════════════
-- TRIGGER 1: Auto-initialize new tenant on user signup
-- Creates rows in: tenants, flow_configs, notification_preferences
-- ═══════════════════════════════════════════════════════════════════
CREATE OR REPLACE FUNCTION public.handle_new_user()
RETURNS trigger AS $$
DECLARE
    new_tenant_id UUID;
BEGIN
    INSERT INTO public.tenants (owner_id, company_name)
    VALUES (
        NEW.id,
        COALESCE(NEW.raw_user_meta_data->>'company_name', 'My SaaS Product')
    )
    RETURNING id INTO new_tenant_id;
 
    INSERT INTO public.flow_configs (tenant_id)
    VALUES (new_tenant_id);
 
    INSERT INTO public.notification_preferences (tenant_id)
    VALUES (new_tenant_id);
 
    RETURN NEW;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;
 
CREATE TRIGGER on_auth_user_created
    AFTER INSERT ON auth.users
    FOR EACH ROW EXECUTE FUNCTION public.handle_new_user();
 
-- ═══════════════════════════════════════════════════════════════════
-- TRIGGER 2: Auto-aggregate analytics_daily on session change
-- Fires on INSERT (new session) and UPDATE (status change)
-- ═══════════════════════════════════════════════════════════════════
CREATE OR REPLACE FUNCTION public.aggregate_session_to_analytics()
RETURNS trigger AS $$
BEGIN
    -- Upsert the row for this tenant + date
    INSERT INTO analytics_daily (tenant_id, date, total_sessions)
    VALUES (NEW.tenant_id, DATE(NEW.created_at), 1)
    ON CONFLICT (tenant_id, date) DO UPDATE SET
        total_sessions = analytics_daily.total_sessions +
            CASE WHEN TG_OP = 'INSERT' THEN 1 ELSE 0 END,
        saved_sessions = analytics_daily.saved_sessions +
            CASE WHEN NEW.status = 'saved'
                  AND (OLD IS NULL OR OLD.status != 'saved')     THEN 1 ELSE 0 END,
        cancelled_sessions = analytics_daily.cancelled_sessions +
            CASE WHEN NEW.status = 'cancelled'
                  AND (OLD IS NULL OR OLD.status != 'cancelled') THEN 1 ELSE 0 END,
        paused_sessions = analytics_daily.paused_sessions +
            CASE WHEN NEW.status = 'paused'
                  AND (OLD IS NULL OR OLD.status != 'paused')    THEN 1 ELSE 0 END,
        total_saved_mrr_cents = analytics_daily.total_saved_mrr_cents +
            CASE WHEN NEW.status IN ('saved', 'paused')
                  AND NEW.saved_mrr_cents > 0
                  AND (OLD IS NULL OR OLD.saved_mrr_cents = 0)
                 THEN NEW.saved_mrr_cents ELSE 0 END;
 
    RETURN NEW;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;
 
CREATE TRIGGER on_session_change
    AFTER INSERT OR UPDATE ON cancellation_sessions
    FOR EACH ROW EXECUTE FUNCTION public.aggregate_session_to_analytics();
 
-- ═══════════════════════════════════════════════════════════════════
-- TRIGGER 3: Auto-update updated_at on all relevant tables
-- ═══════════════════════════════════════════════════════════════════
CREATE OR REPLACE FUNCTION set_updated_at()
RETURNS trigger AS $$
BEGIN NEW.updated_at = NOW(); RETURN NEW; END;
$$ LANGUAGE plpgsql;
 
CREATE TRIGGER set_updated_at_tenants
    BEFORE UPDATE ON tenants
    FOR EACH ROW EXECUTE FUNCTION set_updated_at();
 
CREATE TRIGGER set_updated_at_flow_configs
    BEFORE UPDATE ON flow_configs
    FOR EACH ROW EXECUTE FUNCTION set_updated_at();
 
CREATE TRIGGER set_updated_at_cg_subs
    BEFORE UPDATE ON churnguard_subscriptions
    FOR EACH ROW EXECUTE FUNCTION set_updated_at();
 
CREATE TRIGGER set_updated_at_notif_prefs
    BEFORE UPDATE ON notification_preferences
    FOR EACH ROW EXECUTE FUNCTION set_updated_at();
```

## PART 3 — API Route Architecture
 
### 3.1 Public API Routes (Widget — No Auth Required)
 
These endpoints are called by the embedded `widget.js` script running on client websites.
Authentication is done via HMAC-signed session tokens, not Supabase auth.
 
| Method | Route | Purpose |
|---|---|---|
| POST | `/api/v1/session` | Create session record, issue HMAC token, return flow config |
| POST | `/api/v1/action` | Validate token, execute Stripe offer or cancellation |
| POST | `/api/webhooks/stripe` | Process Stripe events, sync subscription status |
 
**POST `/api/v1/session` — Request / Response:**
```typescript
// Request body (sent by widget.js)
{
  tenant_id: string;            // From data-tenant attribute
  customer_stripe_id: string;   // From data-customer attribute
  customer_email: string;       // From data-email attribute
  subscription_id?: string;     // From data-subscription attribute (optional)
  origin_url: string;           // window.location.href of client page
}
 
// Response (200 OK)
{
  session_id: string;
  token: string;               // HMAC-SHA256 token, 15-min expiry
  flow_config: {
    branding_color: string;
    branding_logo_url: string | null;
    widget_title: string;
    widget_subtitle: string;
    show_powered_by: boolean;
    reasons: FlowReason[];
    offers: Record<string, FlowOffer>;
  };
}
```
 
**POST `/api/v1/action` — Request / Response:**
```typescript
// Request body
{
  session_id: string;
  token: string;
  action: 'apply_discount' | 'pause' | 'cancel' | 'feature_request' | 'calendly';
  reason: string;
  custom_feedback?: string;
}
 
// Response (200 OK)
{ status: 'success'; message: string; }
 
// Error responses
{ error: 'Session not found' }          // 404
{ error: 'Token expired or invalid' }   // 401
{ error: 'Session already completed' }  // 409
{ error: 'Origin not permitted' }       // 403
{ error: 'Stripe integration missing' } // 400
```
 
### 3.2 ChurnGuard Billing API Routes
 
| Method | Route | Auth | Purpose |
|---|---|---|---|
| POST | `/api/v1/checkout` | Supabase session | Create Stripe Checkout for Starter/Pro plan |
| GET | `/api/v1/billing/portal` | Supabase session | Redirect to Stripe Customer Portal |
 
### 3.3 Stripe Webhook Handler
 
```
POST /api/webhooks/stripe
  Verifies: stripe-signature header against STRIPE_WEBHOOK_SECRET
  Handles:
    customer.subscription.updated   → sync plan/status in churnguard_subscriptions + tenants
    customer.subscription.deleted   → set plan='trial', status='cancelled'
    invoice.payment_failed          → set status='past_due', trigger email notification
    customer.subscription.paused    → set status='paused'
```
 
### 3.4 Dashboard Data — Server Actions (No Separate REST Needed)
 
All dashboard data fetching is handled via Next.js Server Actions querying Supabase directly.
This eliminates a separate REST layer and keeps RLS policies in effect.
 
```typescript
// Actions defined in: lib/actions/
getDashboardMetricsAction(tenantId: string)   → DashboardMetrics
getSessionsAction(tenantId, filters, page)    → PaginatedSessions
getAnalyticsAction(tenantId, dateRange)       → AnalyticsData
updateFlowConfigAction(tenantId, data)        → FlowConfig
updateStripeKeyAction(tenantId, apiKey)       → void (validates before saving)
updateNotificationPrefsAction(tenantId, data) → NotificationPreferences
```

## PART 8 — Security Architecture
 
### 8.1 Widget Session Token Flow
 
This is the most security-critical part of the system.
The widget runs on a third-party website, so we cannot trust data it sends without verification.
 
```
CLIENT WEBSITE                    CHURNGUARD SERVERS
 
1. widget.js fires on cancel click
   → reads data-tenant, data-customer,
     data-email from script tag
 
2. POST /api/v1/session ──────────────────────────────►
   { tenant_id, customer_stripe_id,
     customer_email, origin_url }
 
                                   3. Server validates:
                                      - tenant_id exists in DB
                                      - origin_url matches tenant's registered domain
                                      - session_limit not exceeded for this month
 
                                   4. Server creates DB row (status: 'initiated')
                                      Generates:
                                      session_token = HMAC-SHA256(
                                        key: SESSION_HMAC_SECRET,
                                        msg: `${session_id}:${tenant_id}:${customer_stripe_id}:${timestamp}`
                                      )
                                      Sets token_expires_at = NOW() + 15 minutes
 
5. ◄────────────────────────────── Response: { session_id, token, flow_config }
 
6. widget.js opens iFrame:
   /embed/[tenant_id]?session_id=x&token=y
 
7. Customer fills survey, clicks offer
 
8. POST /api/v1/action ───────────────────────────────►
   { session_id, token, action, reason }
 
                                   9. Server validates:
                                      a. Fetch session from DB by session_id
                                      b. Timing-safe compare: token === stored token
                                      c. NOW() < token_expires_at
                                      d. session.status === 'initiated'
                                      e. Origin header matches tenant domain
                                      f. Decrypt tenant's Stripe key from DB
 
                                  10. Execute Stripe API call with tenant's key
                                  11. Update session status in DB
                                  12. Update analytics_daily (via trigger)
 
13. ◄────────────────────────────── Response: { status: 'success' }
 
14. iFrame postMessages parent:
    { type: 'churnguard:close', outcome: 'saved' }
 
15. widget.js removes iFrame overlay
```
 
### 8.2 Stripe Key Encryption
 
```typescript
// lib/security.ts
// Keys are AES-256-GCM encrypted before storage
// Decrypted only inside service-role server actions, never sent to client
 
import crypto from 'crypto';
 
const ENCRYPTION_KEY = Buffer.from(process.env.SESSION_HMAC_SECRET!, 'hex');
 
export function encryptKey(plaintext: string): string {
  const iv = crypto.randomBytes(12);
  const cipher = crypto.createCipheriv('aes-256-gcm', ENCRYPTION_KEY, iv);
  const encrypted = Buffer.concat([cipher.update(plaintext, 'utf8'), cipher.final()]);
  const tag = cipher.getAuthTag();
  return Buffer.concat([iv, tag, encrypted]).toString('base64');
}
 
export function decryptKey(ciphertext: string): string {
  const buf = Buffer.from(ciphertext, 'base64');
  const iv = buf.subarray(0, 12);
  const tag = buf.subarray(12, 28);
  const encrypted = buf.subarray(28);
  const decipher = crypto.createDecipheriv('aes-256-gcm', ENCRYPTION_KEY, iv);
  decipher.setAuthTag(tag);
  return Buffer.concat([decipher.update(encrypted), decipher.final()]).toString('utf8');
}
```
 
### 8.3 Rate Limiting Strategy
 
| Endpoint | Limit | Window | Enforcement |
|---|---|---|---|
| POST `/api/v1/session` | 20 requests | per tenant per minute | Vercel KV or Supabase counter |
| POST `/api/v1/action` | 5 requests | per session_id | DB check on session |
| POST `/api/webhooks/stripe` | 100 requests | per minute | Stripe IP allowlist + signature |
| POST `/api/v1/checkout` | 5 requests | per user per hour | Supabase rate limit policy |
 
### 8.4 Origin Validation
 
When a tenant first successfully connects Stripe (or from their profile settings), we record their registered application domain (e.g., `https://acmesaas.io`). Every widget API request checks that the `Origin` header matches this registered domain. Mismatches return `403 Forbidden`.

## Summary: Decisions & Open Questions
 
### ✅ Finalized Decisions
 
1. **No separate REST API for dashboard** — Server Actions handle all data mutation. Simpler, safer, type-safe.
2. **analytics_daily is DB-trigger-maintained** — No cron job required. Scales to thousands of tenants cheaply.
3. **widget.js is vanilla JS** — React in the embed would add ~40KB gzipped. Unacceptable for a third-party script.
4. **Stripe keys are AES-256-GCM encrypted** — Encrypted by our server before storage, decrypted only during API calls.
5. **HMAC-SHA256 tokens for widget sessions** — 15-minute expiry, one-use, validated server-side. Prevents replay attacks.
6. **flow_config reasons + offers stored as JSONB** — Avoids complex relational joins. The schema is intentionally flexible.
### ⚠️ Implementation Notes for Coding Phase
 
1. The `data-customer` attribute in `widget.js` requires the SaaS founder's server to render the customer's Stripe ID dynamically. Document this clearly in the integrations page instructions.
2. The `Billing` tab in Settings uses ChurnGuard's own Stripe account (not the tenant's Stripe key). These are two completely separate Stripe integrations.
3. All dashboard data mutations should use Server Actions with `revalidatePath()` — not client-side API calls — to keep the cache consistent.
4. The `/embed/[tenant_id]` route should be on Vercel's Edge Runtime (`export const runtime = 'edge'`) for maximum speed.
